## 二、P0 修正

### P0-1 ｜ status.position 每 200ms 同步写盘（现象成立，改法要换）

**现象确认。** 三段证据链成立：`src/stores/status.ts:174` 的 pick 含 `position`；`src/core/player/events.ts:114` 每个 position 事件写入；`native/audio-engine/src/player/background.rs:165` 播放期间 200ms 一次推送；插件对每次 `$subscribe` 无条件 `serialize + setItem`（`node_modules/pinia-plugin-persistedstate/dist/index.js`）。播放期间确为 5Hz 同步 `localStorage` 写入。

**v1 改法的问题：会破坏断点续播。** 冷启动恢复依赖持久化的 `position`：

```ts
// src/core/player/index.ts:1385
const lastPosition = status.position;
// src/core/player/index.ts:1397-1399
if (settings.system.player.rememberLastTrack && lastPosition > 0) {
  await seek(lastPosition);
}
```

`restoreLastTrack()` 在 `status` 从 localStorage 水合之后读取 `status.position`。把 `position` 移出 `pick` 后该值恒为 0，`rememberLastTrack` 静默失效——`src/main.ts:52-53` 的恢复流程照跑，但从头播放。这不是性能优化，是功能回退。

**正确改法 A（推荐，行为不变、改动小）：给持久化换一个节流的 storage 适配器。**

保留 `pick` 不动，只把 `setItem` 合并落盘：

```ts
/** 位置字段播放期间 5Hz 变化，插件每次订阅都会整包序列化；这里合并落盘，避免每 200ms 同步写一次 */
const PERSIST_FLUSH_MS = 1000;
let pendingWrite: { key: string; value: string } | null = null;
let flushTimer: number | null = null;

const flushPending = (): void => {
  if (flushTimer !== null) {
    clearTimeout(flushTimer);
    flushTimer = null;
  }
  if (!pendingWrite) return;
  localStorage.setItem(pendingWrite.key, pendingWrite.value);
  pendingWrite = null;
};

const throttledStorage: Storage = {
  get length() {
    return localStorage.length;
  },
  clear: () => localStorage.clear(),
  getItem: (key) => localStorage.getItem(key),
  key: (index) => localStorage.key(index),
  removeItem: (key) => localStorage.removeItem(key),
  setItem: (key, value) => {
    pendingWrite = { key, value };
    if (flushTimer === null) flushTimer = window.setTimeout(flushPending, PERSIST_FLUSH_MS);
  },
};
```

在窗口隐藏与退出前冲刷，避免丢最后一秒：`window.addEventListener("pagehide", flushPending)`，以及在 `document.visibilitychange` 转为隐藏时调用一次。主窗口隐藏到托盘时 `document.hidden` 会转 true，能覆盖这条路径。

需要知情的一点：`JSON.stringify` 仍会在每次订阅发生（在插件 `persistState` 里），本方案只把**同步落盘**合并掉。若要把整包序列化也去掉，只能走方案 B。

**正确改法 B（更彻底，改动更大）：** 把 `position` 移出 `pick`，改为在边界显式持久化——暂停、seek 结束、切歌、窗口隐藏、退出各写一次。这样 5Hz 的整包序列化也消失。代价是要在 player 里补一处写入口（可参照 `src/stores/queue.ts:40` 的 `save()` 模式），且必须覆盖"隐藏到托盘"这条路径。

**建议：** 先做 A，行为与现状完全一致、可回滚；确认收益后再评估是否值得上 B。

**验证：** DevTools → Application → Local Storage，播放 10s 观察写入频率；Performance 录制 5s 搜 `setItem`，改前应每 200ms 命中一次，改后应为 ≤1Hz 的合并写。**同时必须回归"重启后断点续播仍生效"**，这是 v1 漏掉的验收项。

### P0-2 ｜ 任务栏进度未节流（成立）

**确认。** `electron/main/ipc/player.ts:202` 每个 position tick 无条件调用 `setTaskbarProgress`；`electron/main/window/main.ts:287-295` 落到 `win.setProgressBar`，即 main → browser 进程的系统调用。5Hz 推送对应约 1Hz 的视觉需求，4/5 是浪费。

**改法（在 `setTaskbarProgress` 内部节流即可，不必新建文件）：**

```ts
/** 任务栏进度刷新间隔（毫秒）：系统任务栏刷新率远低于播放位置推送率 */
const TASKBAR_PROGRESS_MIN_INTERVAL_MS = 1000;
let lastSentAt = 0;
let lastMode: "normal" | "paused" | "none" = "none";
```

三种情况必须**无条件**下发，不能被节流吞掉：

1. `progress < 0`（清除）——重置内部状态并立即调用 `setProgressBar(-1)`；
2. mode 变化（`paused` ⇄ `normal`）——`player.ts:136-140` 的暂停分支要立刻显示暂停样式；
3. 首次下发。

其余情况按 `Date.now() - lastSentAt >= TASKBAR_PROGRESS_MIN_INTERVAL_MS` 放行。

**验证：** 在 `setTaskbarProgress` 内临时计数，播放 60s：改前约 300 次，改后应 ≤60 次；并确认暂停/恢复/停止时样式切换即时、无残留。

### P0-3 ｜ SQLite 索引（部分成立，收益与范围都要修正）

**成立的部分：** `excludeCueContainer()`（`electron/main/database/queries.ts:77-78`）确实没有对应索引，schema 只有 `idx_tracks_title` / `idx_tracks_album`（`electron/main/database/index.ts:58-59`）；`idx_tracks_album` 建在 JSON 文本列上，而查询用的是 `json_extract(album, '$.name')`，用不上；better-sqlite3 确实不缓存 prepared statement。

**本地实测（better-sqlite3 13.0.3，内存库复现仓库的 SQL 形态）：**

| 场景                                                                             | 查询计划                                                                                |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 现状 `excludeCueContainer`                                                       | `SCAN tracks` + `LIST SUBQUERY 1 → SCAN tracks`                                         |
| 加 `CREATE INDEX ... ON tracks(cue_audio_path) WHERE cue_audio_path IS NOT NULL` | 子查询变为 `SEARCH tracks USING COVERING INDEX idx_tracks_cue_audio (cue_audio_path>?)` |
| 现状 `json_extract(album,'$.name') = ?`                                          | `SCAN tracks`                                                                           |
| 加表达式索引 `ON tracks(json_extract(album,'$.name'))`                           | `SEARCH tracks USING INDEX idx_tracks_album_name (<expr>=?)`                            |
| 加表达式索引后的 `getAlbumList`                                                  | `SCAN tracks USING INDEX idx_tracks_album_name`（covering）                             |

**收益要重述：** 部分索引让**子查询**从全表扫变成覆盖索引查找；外层查询仍是 `SCAN tracks`——`COUNT/SUM/GROUP BY/ORDER BY RANDOM()` 这类全库聚合本来就要扫全表，索引改变不了。所以收益是"每条复用该片段的查询少一次全表子扫描"，而不是 v1 说的"从全表扫描降为索引查找"。

**范围要修正（v1 的 B 项有误导）：** artist 相关查询**用不上表达式索引**。`getArtistList`（`queries.ts:284`）、`getArtistTracks`（`:312`）、`getLibraryStats` 的 artistCount（`:344`）都走 `json_each(t.artists)` 展开 JSON 数组，planner 只能 `SCAN t` + `SCAN a VIRTUAL TABLE`。要优化得引入 `track_artists(track_id, name)` 关联表或生成列，属于结构改动，**不应混进 P0**。

**"搜索框每次键入触发编译"不成立。** `library:searchTracks` 在渲染层没有任何调用方：只有 `electron/preload/index.ts:203` 暴露接口、`electron/main/ipc/library.ts:113` 注册 handler。本地列表搜索是渲染层在内存里过滤（`src/components/list/SongList.vue:151`）。所以语句缓存的收益主要落在 album/artist/stats 那几个固定 SQL 上，价值有限。

**落地建议：**

1. 两个索引直接加进 `electron/main/database/index.ts:34-59` 的建表块——那里已经是 `CREATE INDEX IF NOT EXISTS` 的惯例，与既有索引放在一起，不需要单开 schema 版本。v1 建议放 `migration.ts` 也能用，只是多一个版本号和迁移分支，收益相同。
2. 语句缓存降级为**可选**：真要做，就按 SQL 文本缓存 `Statement`，动态占位符的 `getTracksByIds`（`queries.ts:373`）按占位符个数做 key。没有实测收益就回滚。
3. artist 维度单独立项，别塞进 P0。
4. 可选清理：表达式索引建好后，`idx_tracks_album`（原 JSON 文本索引）在仓库里已无查询使用，可考虑删除以省插入开销；需要时再单独评估。

**验证：** 5 万首库上 `EXPLAIN QUERY PLAN` + 专辑页/歌手页/统计页前后耗时对比。注意歌手页不会因为这两个索引变快，别把它算进收益。

### P0-4 ｜ media-ctrl 未真正按需（成立）

**确认。** `electron/main/services/media.ts:29-53` 的 `ensureLoaded()` 被 `setMetadata/setPlayState/setTimeline/setRate/setVolume`（`:70-86`）无条件调用；`setTimeline` 在 position tick 上（`player.ts:199`），所以关闭系统媒体控件后第一次播放仍会 `loadNativeModule("media-ctrl.node")` 并 `initialize()`。

**改法（补充实现细节）：** 把配置门放在 setter 上做早退，让 `enable()` 保持"显式加载并启用"的唯一入口：

```ts
/** 系统媒体控件是否启用；关闭时不加载原生模块 */
const isEnabled = (): boolean => store.get("media.systemMediaControls");

export const setMetadata = (param: MetadataParam): void => {
  if (!isEnabled()) return;
  safeCall(() => ensureLoaded()?.setMetadata(param));
};
```

同时**删掉** `ensureLoaded()` 内 `if (mediaConfig.systemMediaControls) mc.enable();` 那段——门控上移后它只会和 `enable()` 重复。`disable()` / `shutdown()` 保持 `mc?.` 形式，不触发加载。事件注册在 `ensureLoaded()` 内，门控后只有真正启用时注册，语义正确。

**验证：** `systemMediaControls: false` 下冷启动并播放，确认主进程不再加载 `media-ctrl.node`（加一条日志或对比主进程 `workingSetSize`）。

## 三、P1 修正

### P1-1 ｜ 暂停期间的 RAF（部分成立，措辞与频率都要改）

**影响范围比 v1 描述的窄。** `usePlaybackTime` 只在全屏播放器展开期间运行：`src/components/player/FullPlayer/index.vue:78` 在 `onBeforeEnter` 调 `startTick()`，`:85` 在 `onBeforeLeave` 调 `stopTick()`。所以不存在"后台一直跑 60fps RAF"。真正与播放状态解耦的是 AMLL 的 `useRafFn`（`AMLLLyrics.vue:170-175`，在 `:275-282` 中"未冻结且可见"就 `resumeRaf()`，与 `playing` 无关）。

准确表述：**全屏播放器展开且暂停**时，存在 2 条 60fps 循环（外层的 `usePlaybackTime` + AMLL 的 `useRafFn`），AMLL 那条是刻意保留的（弹簧需要收敛）。v1 的"暂停后 60fps 空转"会让读者以为不打开播放器也在烧。

**节流频率修正：** v1 建议降到 1Hz 不可行——弹簧按帧积分，1Hz 会让画面呈阶梯状。若要做，取 10~15Hz，或改成"只在 `setCurrentTime` 被调用时驱动 AMLL 更新"（AMLL 的 `update(delta)` 能吃非均匀 delta）。

**约束不变：** 这一条直接动歌词动画手感，**必须实测帧轨道**，改前改后各录 5s，确认暂停时条带消失且恢复播放无跳变。手感劣化就回滚并登记"已尝试未通过"。

### P1-2 ｜ 虚拟列表 scroll 绕过自己的 RAF（成立）

**确认。** `src/components/ui/SVirtualList.vue:217` 的 `emit("scroll", event)` 在 RAF 门之外，`handleScroll` 的 `pendingScrollTarget` + `requestAnimationFrame(processScroll)` 节流对它无效。消费端 `src/components/list/SongList.vue:215-217` 直接写 `scrollTop.value`，而它被 `canScrollTop`（`:213`）依赖，控制回顶按钮显示。

**改法：** 把 emit 移进 `processScroll`（`:202-212`）。因为 `processScroll` 里拿不到原始 Event，需要多存一个引用：

```ts
let pendingScrollEvent: Event | null = null;

const processScroll = (): void => {
  rafId = null;
  const target = pendingScrollTarget;
  if (!target) return;
  if (pendingScrollEvent) emit("scroll", pendingScrollEvent);
  pendingScrollEvent = null;
  // ...原有范围计算与 reachBottom 逻辑
};
```

**消费方核查（决定这个改法是否安全）：** 直连 `SVirtualList` 的 `@scroll` 只有 `SongList.vue:325` 一处。`src/pages/Collection.vue:46-53` 与 `src/pages/Artist.vue:54-61` 的 `handleListScroll` 订阅的是 SongList 再抛出来的事件，逻辑是"滚动超过 10px 收起头部"，最多延后一帧，无感。`reach-bottom` 本就在 `processScroll` 内，不受影响。

### P1-3 ｜ 启动路径同步 IO（成立）

三条子项复核均属实：

- `electron/main/store/index.ts:62-72` 的 `init()` 无条件 `flushImmediate(data)`，且发生在模块求值期，早于 `initApp()` 的第一个埋点。
- `electron/main/utils/logger.ts:19-32` 的 `autoCleanLogs` 用 `readdirSync` + 逐文件 `statSync` + `unlinkSync`，由 `core/index.ts:83` 的 `initLogger()` 触发；`core/index.ts:84` 的埋点在其之后，这段耗时确实没被计入。
- 现有埋点只有 `core/index.ts:84`、`core/index.ts:128`、`electron/main/window/main.ts:92` 三处，`registerIpcHandlers()` / `initDatabase()` / `createMainWindow()`（`core/index.ts:105-109`）之间无打点。

**补充实现要点：**

- store 那条：`init()` 里已经把文件读成文本并 parse 过了，把原始文本留着，与 `deepMerge + migrations` 后的序列化结果比较，**不同才** `flushImmediate`。注意迁移改过数据时必须写回。
- `autoCleanLogs` 改 `fsp` 后 fire-and-forget（不 await）；保持不抛异常，改为写日志而不是静默吞掉。
- 顺序：**先只补打点**，10 次冷启动取中位数，用数据决定后两条值不值得做。不打点就改，违背仓库"没有度量就不改"的方法论。

### P1-4 ｜ 孤儿清理的同步 existsSync（成立，有更优解）

**确认。** `electron/main/services/songCache.ts:193-199` 在 `known`（来自数据库的文件名集合）上逐个 `fs.existsSync`。但同一函数在 `:165` 已经执行过 `entries = await fsp.readdir(cacheDir)`——目录内容就在手边，**不需要再发任何 syscall**：

```ts
const present = new Set(entries);
for (const filename of known) {
  if (!present.has(filename)) {
    const row = findByFilename(filename);
    if (row) deleteByKey(row.cacheKey);
    missingRows += 1;
  }
}
```

v1 建议的 `fsp.access` 或 `Promise.all` 只是把同步 syscall 换成异步 syscall，数量没少；用 `entries` 才是真正的 O(1) 内存判断。

## 四、v1 中明确不要执行的项

1. **P2-1：不要删除 `@pixi/*` 依赖。** 这 7 个包是 `@applemusic-like-lyrics/core` 的 peerDependencies，其产物 `node_modules/@applemusic-like-lyrics/core/dist/amll-core.mjs:3-9` 在模块顶层 `import` 了 `@pixi/app`、`@pixi/core`、`@pixi/display`、`@pixi/filter-blur`、`@pixi/filter-bulge-pinch`、`@pixi/filter-color-matrix`、`@pixi/sprite`。而该库被 `src/components/player/Lyrics/AMLLLyrics.vue:3-6` 静态引入。删掉依赖会让 AMLL 歌词引擎在模块解析阶段直接失败。v1 的"全仓源码零命中"只查了直接 import，漏了传递依赖。

2. **P0-1：不要直接把 `position` 从 `pick` 移除。** 见上文，会破坏 `rememberLastTrack` 断点续播。

## 五、P2 修正

### 10.3 P1-1 实际落地的部分

只做了 physics 路径的空转剔除：`FullPlayer/index.vue` 在**暂停且非 seek 且推送值与上次完全相同**时跳过 `setCurrentTime`，RAF 不停帧。依据是 `playback.getCurrentTime()` 在暂停态返回常量、而 `lyric-dom` 的 `onAnimationFrame` 本来就有 `playTime !== lastProcessedTime` 早退，所以逐帧推同一个值是纯空转；弹簧动画仍由 `lyric-dom` 自身的 60fps 循环驱动，观感不变。歌词偏移、时长、播放态、seek 任一变化都会立刻放行，不存在"改了偏移要等一秒才见效"的问题。
