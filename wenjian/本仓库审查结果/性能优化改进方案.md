## 二、P0 — 立即修复（有实测证据，改动小、收益确定）

### P0-1｜status.position 被纳入持久化，播放期间每 200ms 同步写盘

**严重程度：高 ｜ 位置：渲染进程 ｜ 改动量：约 5 行**

这是本次审查唯一一处"高频 × 同步 IO"的组合，是收益最确定的一项。

**完整证据链（三段均已亲自核实）**：

1. `src/stores/status.ts:167-181` — `persist.pick` 白名单第 7 项包含 `"position"`：

   ```ts
   persist: {
     storage: localStorage,
     pick: ["playIndex", "repeatMode", ..., "volume", "position", ...],
   }
   ```

2. `src/core/player/events.ts:113-114` — 每个 position 事件写入该字段：

   ```ts
   const adjusted = playback.setCurrentTime(event.data.position);
   status.position = adjusted;
   ```

3. `node_modules/pinia-plugin-persistedstate/dist/index.js:66,96` — 插件对每次 `$subscribe` 无条件序列化写盘，**无节流、无去重**：

   ```js
   storage.setItem(key, toStorage); // :66
   store.$subscribe((_mutation, state) => persistState(state, p), { detached: true }); // :96
   ```

4. `native/audio-engine/src/player/mod.rs:291` — 播放时启动 200ms 位置推送定时器（`:90` 注释"每 200ms 推送一次位置"）。

**影响机制**：`localStorage.setItem` 是同步 API，序列化 + 写盘全部占用主线程，且精确落在每两个动画帧之间。它同时放大了响应式触发面——`position` 被 `progress` 等 computed 依赖，每次写入都会把渲染开销叠加到帧预算上。对笔记本的续航影响是持续的，因为播放是本应用的主场景。

**建议改法**：把 `position` 从 `pick` 中移除。若产品确实需要"重启后恢复播放进度"，改为在切歌和退出时显式写一次——仓库内 `src/stores/queue.ts:40-43` 已有 `save()` 模式可直接参照，不必另立一套。

**预期收益**：播放期间主线程每 200ms 少一次 `JSON.stringify` + 一次同步磁盘写。这是本次审查中唯一能"改 5 行、收益立刻可见"的一项。

### P0-2｜任务栏进度未节流，每 200ms 一次跨进程系统调用

**严重程度：中高 ｜ 位置：主进程 ｜ 改动量：新建 1 个文件**

**证据**：

- `electron/main/ipc/player.ts:202` — 每个 position tick 无条件调用：
  ```ts
  if (store.get("system.taskbarProgress") && durMs > 0) setTaskbarProgress(posMs / durMs);
  ```
- `electron/main/window/main.ts:293` — `win.setProgressBar(progress, { mode: ... })`。

**影响机制**：`setProgressBar` 的调用链是 主进程 → 浏览器进程 → Windows 任务栏，是本热路径上最贵的同步操作。而任务栏进度条的肉眼刷新需求约 1Hz，推送率却是 5Hz——**4/5 的调用是纯浪费**。

**建议改法**：新建 `electron/main/window/taskbarProgress.ts`，按仓库约定用常量而非可配置开关：

```ts
/** 任务栏进度条刷新间隔（毫秒）：系统任务栏刷新率远低于播放进度推送率，无需逐 tick 同步 */
const TASKBAR_PROGRESS_MIN_INTERVAL_MS = 1000;
```

内部保存 `lastSentAt` / `lastRatio`，并在暂停态变化时立即冲刷一次（`player.ts:136-140` 已有暂停分支，走同一冲刷入口）。

**预期收益**：主进程播放期间每分钟减少约 240 次跨进程系统调用。

### P0-3｜SQLite 缺两个关键索引，且每次查询重新 prepare

**严重程度：中高 ｜ 位置：主进程 ｜ 改动量：约 30 行 + 1 条迁移**

**问题 A：`excludeCueContainer()` 子查询无索引，出现在每一条查询上**

`electron/main/database/queries.ts:77-78`：

```ts
const excludeCueContainer = (col = "path"): string =>
  `${col} NOT IN (SELECT cue_audio_path FROM tracks WHERE cue_audio_path IS NOT NULL)`;
```

该片段被 `getTrackCount`（:83）、`searchTracks`（:226）、`getAlbumTracks`（:302）、`getArtistTracks`（:314）、`getLibraryStats`（:329,337,348,356）等**全部**列表/计数/搜索查询复用，而 schema（`index.ts:58-59`）只建了 `idx_tracks_title` 和 `idx_tracks_album`，`cue_audio_path` 无索引。5 万首曲库上每次搜索都要多扫一遍全表。

**问题 B：`json_extract()` 用不上现有索引**

`index.ts:59` 的 `CREATE INDEX idx_tracks_album ON tracks(album)` 建在 JSON **文本列**上，而 `queries.ts:302` 用的是 `json_extract(album, '$.name') = ?` —— 函数表达式**无法使用该索引**。同类全表扫描还有 `getAlbumList`（:263）、`getArtistList`（:284）、`getLibraryStats`（:335,344）。

**问题 C：better-sqlite3 不缓存 prepared statement**

`queries.ts` 中 11 处查询每次都调 `db.prepare()`，每次都要把 SQL 编译成字节码。搜索框每次键入都触发一次完整编译。

**建议改法**：

1. 在 `migration.ts` 补建两个索引：
   ```sql
   CREATE INDEX IF NOT EXISTS idx_tracks_cue_audio ON tracks(cue_audio_path) WHERE cue_audio_path IS NOT NULL;
   CREATE INDEX IF NOT EXISTS idx_tracks_album_name ON tracks(json_extract(album, '$.name'));
   ```
   第一个是部分索引（体积极小），第二个是 SQLite 原生支持的表达式索引。
2. 在 `database/index.ts` 建模块级 `Statement` 缓存 + `stmtFor(sql)` helper。符合仓库"3+ 处使用才抽 helper"的约定；`getTracksByIds`（:373）这类动态占位符 SQL 保持每次 prepare。

**预期收益**：曲库越大收益越明显。预期专辑页、歌手页、搜索框在万级曲库上从全表扫描降为索引查找。

### P0-4｜media-ctrl "按需加载"实际未按需

**严重程度：中 ｜ 位置：主进程 ｜ 改动量：约 8 行**

**证据**：

- `electron/main/services/media.ts:78-79` — 无条件走 `ensureLoaded()`：
  ```ts
  export const setTimeline = (param: TimelineParam): void =>
    safeCall(() => ensureLoaded()?.setTimeline(param));
  ```
- `media.ts:45` — 配置判断只包住了 `enable()`：
  ```ts
  if (mediaConfig.systemMediaControls) {
    mc.enable();
  }
  ```
- `electron/main/ipc/player.ts:199` — 每个 position tick 都调 `setTimeline`。

**影响机制**：用户关闭"系统媒体控件"后，第一次播放 tick 仍会 `loadNativeModule("media-ctrl.node")` + `initLogger` + `initialize()`，`.node` 常驻主进程内存。这与 `media.ts:24-28` 注释声明的意图、以及 commit `5035017`（"媒体控制改按需加载"）的意图都不符——**加载与启用被耦合在了一起**。

**建议改法**：把配置判断提到 `ensureLoaded()` 之前，让"是否加载"和"是否 enable"共用同一个门。关闭态下 `setTimeline` / `setMetadata` / `setPlayState` 直接早退。

## 三、P1 — 建议排期（结构性收益，需要实测驱动）

### P1-1｜暂停后渲染进程仍有 60fps RAF 空转

**严重程度：中高 ｜ 位置：渲染进程**

**证据**：

- `src/composables/usePlaybackTime.ts:19-21` — `tick` 无条件续帧，无 `isPlaying()` 判断：
  ```ts
  const tick = (): void => {
    onTick(Math.round(getCurrentTime()), Math.round(getDuration()), isPlaying());
    rafId = requestAnimationFrame(tick);
  };
  ```
- `src/components/player/Lyrics/AMLLLyrics.vue:275-282` — 显式保持 RAF：
  ```ts
  if (!frozen && !hidden) {
    // 只要未冻结且可见，就持续运行 RAF 维持渲染（即使暂停也要保持画面）
    resumeRaf();
  ```
- `FullPlayer/index.vue:60` 外层还有一条 `usePlaybackTime`，AMLL 引擎内部第三条 → 展开全屏播放器时并行 2~3 条 60fps 循环。

**影响机制**：暂停后仍以 60fps 驱动整棵歌词行的弹簧与逐字计算。注意 AMLL 那处的"即使暂停也要保持画面"是**有意为之**（弹簧需要收敛），不是 bug——但"保持画面"不等于"必须 60fps 驱动"，降到 1~5Hz 节流同样能收敛，且肉眼无差别。

**建议改法**：

1. `usePlaybackTime` 的 `tick` 在 `!isPlaying() && !seeking` 时改低频（1Hz）而非停帧——停帧会导致恢复播放时第一帧跳变。
2. 合并调度：保留一条 RAF 推时间，歌词引擎在 `setCurrentTime` 被调用时才更新。

**⚠️ 必须实测再改**：此项直接触碰歌词动画的手感，**不得凭推理合入**。改前改后各录 5 秒 Performance 帧轨道，确认"暂停时条带消失"且"恢复播放时无跳变"。若手感劣化，保留原实现并在 PERF 记录中登记为已尝试未通过。

### P1-2｜虚拟列表的滚动事件绕过了自己的 RAF 节流

**严重程度：中 ｜ 位置：渲染进程 ｜ 改动量：约 3 行**

**证据** — `src/components/ui/SVirtualList.vue:214-222`：

```ts
const handleScroll = (event: Event): void => {
  const target = event.target as HTMLElement;
  if (!target) return;
  emit("scroll", event); // :217 ← 在 RAF 门之外
  pendingScrollTarget = target;
  if (rafId === null) {
    rafId = requestAnimationFrame(processScroll);
  }
};
```

消费端 `src/components/list/SongList.vue:215-216` 在这个 `@scroll` 上写响应式 ref：

```ts
const onScroll = (event: Event): void => {
  scrollTop.value = (event.target as HTMLElement).scrollTop;
};
```

`scrollTop` 被 `canScrollTop`（:213）依赖并用于控制回顶按钮（:722 `v-if`）。触控板滚动可达 60~120Hz，即**每帧一次响应式写入 + 一次 computed 重算 + 潜在重渲染**，而组件自己辛苦实现的 RAF 节流对它完全无效。

**建议改法**：把 `emit("scroll", event)` 移入 `processScroll`（:202-212）内，与范围计算同帧执行。改动 3 行，语义不变。

### P1-3｜启动路径上的同步 IO 与缺失的度量

**严重程度：中 ｜ 位置：主进程**

**问题 A：配置 store 每次启动无条件重写配置文件**

`electron/main/store/index.ts:62-72`：

```ts
const init = (): SystemConfig => {
  const data = deepMerge(defaultSystemConfig, readFile());
  runPendingMigrations(data, configDir);
  flushImmediate(data); // 每次启动都原子重写，即使内容未变
  return data;
};
let data: SystemConfig = init(); // :72 模块求值期副作用
```

且该副作用发生在 `initApp()` **之前**（导入链 `index.ts:1` → `core/index.ts:3` → `window/index.ts:1` → store），因此早于第一个启动埋点。

**问题 B：日志清理在首窗口之前做同步目录扫描**

`electron/main/utils/logger.ts:19-25` 的 `readdirSync` + 逐文件 `statSync`，由 `core/index.ts:83` 在 `initApp()` 最开头调用。日志积累多时阻塞启动，且这段耗时**未被计入**"启动耗时｜日志就绪"（埋点在 `:84`，在调用之后）。

**问题 C：启动打点只有 3 处，关键区段无度量**

现有埋点：`core/index.ts:84`（日志就绪）、`main.ts:93`（主窗口首次显示）、`core/index.ts:128`（应用初始化完成）。中间串行阻塞的 `registerIpcHandlers()`（:105）、`initDatabase()`（:107）、`createMainWindow()`（:109) **彼此之间无任何打点**。

**建议改法**（按顺序做，先测量再优化）：

1. **先只补打点，不改逻辑**——在 :105/:107/:109 各补一条同格式打点，跑 10 次冷启动，看这三段各占多少 ms。这是唯一能确定优化优先级的办法。
2. `init()` 中比较序列化结果，仅当与落盘内容不同时才 `flushImmediate`。
3. `logger.ts` 的 `autoCleanLogs` 改 `fsp` 异步，不 await；或推迟到 `whenReady` 之后。

**注意**：按仓库的性能方法论，**没有度量就不改**。先补打点，用数据决定 2 和 3 值不值得做。

### P1-4｜歌曲缓存孤儿清理使用 N 次同步 `existsSync`

`electron/main/services/songCache.ts:193-199` — 文件列表已用 `await fsp.readdir` 异步读取（:165），紧接着却用同步 API 遍历整个集合：

## 五、明确排除的疑似问题（避免后续重复排查）

以下现象看似问题，经核实**均不是缺陷**，记录在此以免下次重复审查：

1. **任务栏歌词暂停态 5Hz 空转 —— 不成立。**
   `useNowPlayingSync.ts:107` 的 `syncRevision.value += 1` 确实只在暂停分支自增，看似空转；但追到源头 `native/audio-engine/src/player/mod.rs:328` — **`pause()` 会调用 `stop_position_timer()`**，暂停后原生根本不再产生 position 事件，5Hz 推送不存在。

2. **`windows/` 全域缺 `visibilitychange` 门控 —— 影响有限。**
   该窗口使用 frameless + `show: false` 常驻任务栏，`isVisible()` 语义与普通窗口不同，主窗口侧的 `isVisible()` 门（`player.ts:198`）已足够。此项从"约定违反"降级为可选。

3. **`store.get()` 热路径成本 —— 可忽略。**
   `store/index.ts:93-95` 是纯内存 dot-path 取值，无文件 IO、无深拷贝。虽在每 tick 调用，但代价仅一次 `String.split`，不值得改。

4. **IPC 监听器重复注册 / 定时器泄漏 —— 未发现。**
   `registerIpcHandlers` 仅调一次；托盘 `initTray` 有幂等早退（`tray.ts:133-134`）；设备监听有配对清理（`device.ts:159-160`）。这块是健康的。

5. **渲染层 FFT / 频谱高频推送 —— 不存在。**
   `electron/` 与 `src/` 全量检索 `fft|spectrum` 均零命中。

| P0-1     | DevTools → Application → Local Storage，播放 10s 观察写入频率；Performance 录制 5s 搜索 `setItem`，改后应零命中 |
| P0-2     | 临时在 `setTaskbarProgress` 内计数，播放 60s：改前 ≈300 次，改后 ≤60 次                                         |
| P0-3     | 5 万首库上 `EXPLAIN QUERY PLAN`，应从 `SCAN tracks` 变为 `SEARCH tracks USING INDEX`                            |
| P0-4     | `systemMediaControls: false` 下冷启动，对比主进程 `workingSetSize`                                              |
| P1-1     | Performance 帧轨道：暂停时 60fps 条带应消失，恢复播放时无跳变                                                   |

**通用纪律**（沿用仓库性能约定）：

- **一次只改一项**，分别测量。三项打包上线则无法归因。
- **改动前后必须用同一种方式、同样条件测量**。冷缓存测基线、热缓存测结果是自欺。
- **提升幅度必须超过运行间波动**。3% 的提升落在 ±5% 波动内等于没提升。
- **落在噪声内的改动一律回滚**。中性改动不是"保留"，是给未来背维护成本。
- **每项改动前后跑 `pnpm test`**，正确性优先于指标。
- 建议在本文件追加"尝试记录"表（想法 / 基线→结果 / 保留或回滚 / 原因），避免半年后有人重试同一个已失败的方案。
