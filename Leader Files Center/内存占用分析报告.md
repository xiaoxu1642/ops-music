## 一、结论摘要

**内存高不是 JS 代码写漏了，而是三件事叠加：多窗口的结构性开销（约六成）、图片解码位图的严重过采样、以及一条确实存在的单调增长曲线。**

| 判断                                 | 证据强度   | 关键数据                                                                                       |
| ------------------------------------ | ---------- | ---------------------------------------------------------------------------------------------- |
| JS 堆没有泄漏                        | 确证       | 主窗口 JS 堆全程 16–22MB，强制 GC 后 17.4MB。相对 234MB 的工作集，JS 对象只占 7%               |
| 结构性多进程开销是最大头             | 确证       | 空载对照：taskbar-lyric 窗口仅 47 个 DOM 元素、4.3MB JS 堆、1 张图 → 工作集仍 97–122MB         |
| 图片解码位图是 renderer 内最大可控项 | 确证       | 首页 68 张图解码 34.5MB，按显示尺寸只需 12MB；搜索专辑页 88 张 46.7MB                          |
| 存在真实的不回收增长                 | 确证       | 主窗口 214→228→247MB（30 分钟）；重启后 162→234MB（9 分钟）；事件监听器 396→549 且离开页面不降 |
| 本地音乐库过大                       | **已排除** | library.db 仅 0.3MB，封面磁盘缓存仅 1 个文件 18.7KB                                            |
| 歌词/历史/队列等 store 累积          | **已排除** | 切歌即清空，且有 MAX_HISTORY=500 等硬上限                                                      |

最坏实测总占用 **1195MB**（18:05 采样：主窗口 + 任务栏歌词 + 灵动岛 + Audio Service + Video Capture 同时在）。典型稳态 **750–960MB**。

## 三、内存构成拆解（以典型稳态 754MB 为例）

```
Browser 主进程            186MB  24.7%   Node + 5 个 .node 模块 + SQLite + 在线 API 缓存
Tab(main) 渲染进程        234MB  31.0%   ├ JS 堆 17MB / 图片解码 35MB / 其余 ~180MB 为
                                        │   Chromium 渲染进程固有开销（V8 isolate、字体、
                                        │   Skia、合成器、光栅线程）
GPU 进程                  161MB  21.4%   透明窗口 + backdrop-filter + 大面积合成
Tab(taskbar-lyric)        122MB  16.2%   ← 内容只有 47 个 DOM 节点
Utility(Network Service)   51MB   6.8%
```

**关键比例**：真正承载应用逻辑的主窗口只占 31%，而一个近乎空白的任务栏歌词窗口占了 16%。这说明优化重点不在"少建对象"，而在"少开窗口、少喂位图"。

另外注意 `electron/main/window/create.ts:11-12` 设定 `minWidth: 1280, minHeight: 800`——窗口无法缩小，合成面积有下限，GPU 进程内存也因此压不下来。

## 四、根因排序

### R1 · 多窗口结构性开销（占约 60%，设计代价而非缺陷）

每个 `BrowserWindow` 是独立渲染进程，空载基线实测 **97–122MB**。当前常驻：主窗口 + taskbar-lyric；按需：desktop-lyric、dynamic-island；调试：DevTools 独立占 170–172MB。

同时 `electron/main/window/main.ts:111-117` 关闭主窗口时 `event.preventDefault(); mainWindow?.hide()`——**关窗不销毁**，234MB 常驻。`hide` 之后 Chromium 只是节流渲染，进程与已分配内存全部保留。

实测叠加成本：

- 开任务栏歌词 +122MB
- 开灵动岛 +139MB
- 开桌面歌词 再 +约 130MB
- 开 DevTools +170MB
- 用过一次歌曲识别：Audio Service +98MB、Video Capture +133MB，且这两个 utility 在后续采样中不再释放（17:56 与 18:05 两次采样均恒为 98/133）

### R2 · 图片解码位图过采样（renderer 内最大可控项）

按"图片按显示尺寸取图"的约定逐条对照，实测到 4 处违反：

| #   | 位置                                                                          | 实际                                                                           | 应该                             | 单帧代价                   |
| --- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | -------------------------------- | -------------------------- |
| a   | `src/components/layout/NavUser.vue:85-91` 顶栏用户头像                        | 网易云原图 **1192×1192** 裸 `<img>`，无 `withPicSize`、无 `decoding`/`loading` | 显示在 **32×32** 圆角容器        | **5.42MB**，常驻顶栏不释放 |
| b   | 内置默认封面 `assets/song-*.jpg`                                              | **500×500**                                                                    | 卡片 **151×151**，首页 12 张共用 | 11.4MB（去重后 0.95MB）    |
| c   | `src/components/list/SongList.vue:584` 歌曲行封面                             | `SImg :src="item.cover"`（300px）                                              | 行高 **size-12 = 48px**          | 6.25 倍过采样，每行 0.34MB |
| d   | `electron/main/apis/qqmusic/modules/search.ts:157,170,182` 专辑/歌手/歌单搜索 | `cover: secureUrl(album.pic)` **完全没有尺寸约束**                             | 300px                            | 原图直进 `<img>`           |
| e   | `electron/main/apis/kugou/core/config.ts:83-87` `fillCover`                   | 仅替换 `{size}` 占位符，URL 不含占位符时**原样返回大图**                       | 300px                            | 同上                       |

(a) 是最典型的：一张图 5.42MB 解码，显示面积 32×32 只需 4KB，**浪费 1350 倍**，而且它挂在顶栏，整个应用生命周期内常驻。(d)(e) 解释了 A3 场景 88 张图 46.7MB 的来源。

作为对照，网易云侧 `src/utils/format/netease.ts:80-81` 的映射是正确的（`cover` 走 `?param=300y300`），但 `coverOriginal` 取 `?param=1024y1024`，被 `src/components/player/FullPlayer/PlayerBackground.vue:47,57` 当作模糊背景源，叠加 `:181` 的 `filter: blur(45px) saturate(1.2)` + `transform: scale(1.5)` 全屏层——这是全屏播放器打开时 GPU 进程涨到 160–195MB 的直接原因。

### R3 · 确实存在的不可回收增长

三个来源，按贡献排序：

1. **`KeepAlive :max="10"`**（`src/layouts/MainLayout.vue:139`）。缓存 10 个页面组件，连带其 DOM 子树与 `<img>` 引用。实测 Nodes 3465 对 document 内 1335，约 2100 个节点长期驻留；监听器 396→549 不回落也来自这里。每访问一个新页面就固化一份。
2. **合成层累积**。taskbar-lyric 在几乎无 JS 对象的前提下 9 分钟涨 25MB，只能归因于 5Hz `position-sync`（`electron/main/services/nowPlaying.ts:131-142`）驱动的文本重排与 Skia/GPU 缓存。`electron/main/ipc/nowPlaying.ts:31` 虽然传了 `visibleOnly=true`，但任务栏歌词窗口是嵌入任务栏的，`isVisible()` 恒为真，门控对它无效。
3. **图片解码缓存随浏览的封面数增长**。A3→A7 图片解码量 46.7 → 34.5MB，但工作集只从 238 回到 242，说明 Chromium 未立即归还解码位图。

### R4 · 主进程 186MB 的固有成本

启动即加载 5 个 native 模块：better-sqlite3、media-ctrl（SMTC + Discord RPC）、taskbar-thumbnail、audio-engine、audio-capture。其中两处可以按需化：

- `electron/main/services/media.ts:48` 无条件 load media-ctrl，`:61-64` 才按设置决定是否启用——**功能关掉时 .node 仍驻留**。
- `src/components/layout/NavSearch.vue:305` 无条件渲染 `<RecognitionDialog>`，其 `onMounted` 触发 `recognition:isSupported` IPC，链路 `electron/main/ipc/recognition.ts:16` → `services/recognition/session.ts:260` → `:34` 在**启动时就 load 了 audio-capture.node**，尽管 `isSupported` 本身只判断平台、不打开设备。

常驻大对象（均有界，非累积）：

- `electron/main/services/nowPlaying.ts:25` `currentLyric` 整首歌词常驻，供 SMTC/Discord/MCP 读取，切歌即替换。
- `electron/main/services/thumbnail.ts:15` `lastCover` 永久持有上一首封面**原始字节**，`:62-65` 每次推送另建 256px `NativeImage`（约 256KB 峰值）。

在线 API 响应缓存有界（netease/qqmusic/kugou 各 200 条 LRU、2 分钟 TTL），`electron/main/services/mcp/cache.ts` 上限 500 条，均合格。

## 六、修复建议（按性价比排序）

### P0 · 改动极小，收益确定

1. **头像按显示尺寸取图**：`NavUser.vue:85,111` 改为 `withPicSize(user.profile.avatarUrl, 96)` 并加 `decoding="async"`。省 5.4MB 常驻，一行改动。
2. **默认封面出小图**：`assets/song.jpg` 从 500px 降到 200px，或列表卡片改用缩略图档。省约 10MB（首页）。
3. **列表行封面降档**：`SongList.vue:584` 一类 48px 容器改用 100–150px 档（`withPicSize` 已支持任意 size，只需在映射层按用途分档）。首页 + 搜索页合计省 15–25MB。
4. **补齐 QQ/酷狗尺寸约束**：`qqmusic/modules/search.ts:157,170,182` 套用与歌曲一致的 `T002R300x300` 规则；`kugou/core/config.ts:83-87` 在 URL 不含 `{size}` 时追加平台缩放后缀，而不是原样返回。

P0 合计预期：**每窗口省 25–45MB**，且直接压低 GPU 进程合成压力。

### P1 · 针对增长曲线与窗口开销

5. **收紧 KeepAlive**：`MainLayout.vue:139` 的 `:max="10"` 降到 3，或把 Search / 列表类页面从 `cachedViews` 排除。直接对应"监听器 +153 不回落""Nodes 比 DOM 多 2100"。
6. **主窗口隐藏到一定时长后销毁**，或至少提供"关闭时退出"的默认倾向。当前 `hide()` 让 234MB 白占。
7. **歌词窗口的高频门控换成真实可见性**：`isVisible()` 对嵌入任务栏的窗口恒真，应改用 `isMinimized()` + 实际显示状态，或让任务栏歌词在任务栏不可见时降频。对应 taskbar-lyric 9 分钟涨 25MB。
8. **侧边栏歌单接入虚拟列表**（`SMenu.vue:124-129`），并把订阅歌单改为分页拉取。这是唯一会随用户数据量线性增长的常驻 UI。

### P2 · 工程化与规模化前置

9. `media-ctrl`、`audio-capture` 改首次用户动作再 load（省 5–15MB 常驻）。
10. 把 CDP 侧量到的指标做进现有采样日志：在 `logProcessMemory` 里附带 renderer 的 `performance.memory` 与"图片解码总量 / 显示面积比"，让过采样成为可长期观测的回归指标，而不是一次性排查。
11. `lyric_cache` 补 TTL；`electron/main/server/broadcast.ts:12` 的 `wsClients` 在 `stopServer` 时清空（真实泄漏）；`startMcpServer` 的 `runningServer` 赋值时机竞态修掉（`electron/main/services/mcp/http.ts:62,99,115`）。
12. 队列 `queueEntries` / `user.ts` 全量列表加显式上限或分页，赶在媒体库变大之前。

### 附带发现（非内存，但排查时撞见）

- **全仓 0 处 `setPermissionRequestHandler`**，`create.ts:17-30` 也未设置，意味着 media（麦克风/摄像头）权限**无条件放行**。识别功能一旦调用即静默授权，属安全隐患。
- 插件市场接口连续 HTTP 502（`17:58:52`、`:54`、`:55`），存在无退避的连续重试。

## 七、复现方法

安装版默认不暴露 CDP。本次按下列方式接入，无需构建：

```bash
# 1) 结束现有实例（含子进程）
taskkill /PID <main-pid> /T /F

# 2) 带调试端口重启同一个安装版
"C:\Program Files\SPlayer-Next\SPlayer-Next.exe" --remote-debugging-port=9222
```

采集要点（脚本留在 `C:\Users\Administrator\.qoder\tmp\splayer-mem\`）：

- `cdp2.mjs` / `bigimgs.mjs`：遍历 `<img>`，按 `naturalWidth × naturalHeight × 4` 算解码位图，与 `clientWidth` 对比得出过采样倍数，并回溯 DOM 归属。这是本次最有效的定位手段。
- `driver2.mjs`：CDP 驱动路由与切歌，逐步采 `Performance.getMetrics` + `HeapProfiler.collectGarbage`，用于区分"真占用"与"可回收缓存"。
- 注意：主窗口被最小化或遮挡时 `document.visibilityState === 'hidden'`，Chromium 会节流渲染，此时场景切换看不到 DOM 变化。用应用自身 IPC 唤回：`window.api.system.focusMainWindow()`。
- Electron 的 browser endpoint 不支持 `Browser.getWindowForTarget`，别指望它调整窗口。

## 八、一句话给决策

如果只做一件事：**先做 P0 的头像和列表封面降档**（改动不到 10 行，每窗口省 25–45MB）；如果想真正改变"这软件吃 1GB"的观感，必须动 P1 的窗口策略——因为数据已经证明，这个应用最大的内存买家不是它的 JavaScript，而是它同时养着的多个渲染进程和它们背后的 GPU 合成层。
