## 0. 先说三件必须先看的事

### 0.1 这个项目当前没有版本控制

`C:\KaiFa\SPlayer-Next` **不是 git 仓库**（已确认：`git rev-parse` 返回 not a git repository，目录无 `.git`）。而本次改造要删除 2 个 native crate 的一部分、2 个完整窗口目录、约 30+ 个源文件。

**没有版本控制的批量删除不可回滚。** 所以 B0 批次必须先建仓库并打基线 tag，这一步不做完不许进入 B1。

### 0.2 退役 TTML 有一个你可能没料到的后果

盘点确认：**网易云在线歌词只有 LRC 行级时间戳，TTML 是它唯一的逐字（word-level）与音译来源**（`electron/main/apis/common/lyric/netease.ts` 引用 TTML 链路）。酷狗/QQ 的 krc/qrc 不受影响。

所以你只用网易云的前提下，退役 TTML 的实际后果是：

- 网易云歌曲在主播放器的**逐字扫光高亮**退化为整行扫光
- **音译（romanization）** 消失
- 任务栏歌词的逐字扫光同样退化为整行（`TaskbarLyricLine.vue:16` 的 `useKaraoke` 依赖 `line.words`，无数据时 words 长度为 1）

行级歌词本身、翻译、歌词同步、任务栏歌词同步**都不受影响**。

如果你觉得逐字高亮可以放弃，就照原计划删；如果想保留逐字，正确做法是**只删 TTML 的缓存表与下载导出，保留 AMLL TTML DB 在线覆盖链路**——这是一条独立分支，可拆。这个选择留在 B5 批次前决定即可，不阻塞前面各批。

### 0.3 退役不等于内存问题解决了

必须诚实：**这批退役主要消除的是内存上限和长尾，稳态收益有限。** 量化见第 2 节。真正让"这软件吃 1GB"改观的是报告里 P1 的窗口策略与图片降档，那部分我作为 B12 一并纳入本方案。

## 2. 内存收益量化（对齐实测数据）

实测基线（`app.getAppMetrics()` 采样，见分析报告）：典型稳态 **754MB**，最坏 **1195MB**。

| 批次          | 收益项                                                                             | 量级                          | 性质                                                       |
| ------------- | ---------------------------------------------------------------------------------- | ----------------------------- | ---------------------------------------------------------- |
| B2 识曲       | Audio Service 98MB + Video Capture 133MB                                           | **−231MB**                    | 实测触发后不再释放，属**消除长尾**；不用识曲的用户本来不吃 |
| B2 识曲       | `audio-capture.node` 启动即载（`NavSearch.vue:305` → `recognition/session.ts:34`） | −5~15MB 主进程                | 确定                                                       |
| B6 灵动岛     | 独立渲染进程                                                                       | **−139MB**                    | 实测值（18:05 采样）                                       |
| B6 桌面歌词   | 独立渲染进程                                                                       | 约 −130MB                     | 同类 renderer 推算，未实测（采样期内你未开过它）           |
| B4 外部 API   | `wsClients` 无上限残留（分析报告里唯一确认的主进程真泄漏）                         | 消除累积                      | 定性                                                       |
| B5 TTML       | `lyric_ttml_cache` 表（存整首 TTML 正文）                                          | 磁盘可能 −数百 MB；RSS 影响小 | 磁盘为主                                                   |
| B12 图片降档  | 头像 1192→96px、默认封面 500→200px、列表 300→150px                                 | **每窗口 −25~45MB**           | 实测可复现，见分析报告 P0                                  |
| B12 KeepAlive | `:max="10"` → 3                                                                    | 消除监听器 396→549 不回落     | 抑制增长                                                   |

**合并效果**：

- 稳态：754MB → 约 **710–730MB**（主要来自 B12 图片降档；退役项在稳态里本来不占）
- 最坏场景：1195MB → 约 **790MB**（灵动岛/桌面歌词/识曲长尾全部不可能再出现）
- 若同时执行 B12 的窗口策略（主窗口隐藏后超时销毁）：关闭主窗口后驻留从 754MB 降到约 **400MB**

结论：**这批改造的价值主要在"可预测"和"减面积"，不在"降稳态"。** 想要稳态明显下降，B12 才是关键。

### 5.1 配置迁移（必须新写，当前是空的）

关键事实：`electron/main/store/utils.ts:32-34` **显式把 stored 中 defaults 里没有的 key 原样搬进结果**，所以删掉 defaults 里的 key **不会自动清理**，`lastfm` / `externalApi` / `mcp` / `media.discord` / `system.networkProxy` / `system.neteaseRealIp` / `streaming` / `desktopLyric` / `dynamicIsland` 会永久留在老用户 `settings.json` 并被继续写盘。

> ⚠️ **备份导入是第二条污染路径**：`store/index.ts:129-133` 的 `replaceAll` 同样走 `deepMerge`，老备份文件会把已退役 key 重新注入。必须在 `replaceAll` 之后再跑一次同一迁移。

### 5.2 数据库迁移

## 6. TaskBarLyrics 能力回补（第 6 条）

先给结论：**值得补的只有 3 项，且第 1 项与你退役 TTML 的决定正好互补。**

TaskBarLyrics 是 Python 3.11+ / PySide6 写的**网易云桌面版（cloudmusic.exe）专用**任务栏歌词工具，靠 SMTC 读播放状态。它的"技术"部分（Qt 窗口、SMTC、任务栏嵌入、LRC 解析）SPlayer-Next **全部已有，且多数更强**：

| 维度               | 谁更强     | 依据                                                                                                           |
| ------------------ | ---------- | -------------------------------------------------------------------------------------------------------------- |
| 歌词格式覆盖       | **S 远强** | S 用 `lyric-kit` 支持 yrc/qrc/krc/ttml 逐字；T 仅 LRC，`config.py:78` 自己注明 `sweep_style=word` "待词级数据" |
| 时长校验           | **S 强**   | `apis/common/lyric/utils.ts:70-145` 打分制（±5s 加分 / 20s 剔除）vs T 的二值硬拒 ±5000ms                       |
| 编码探测           | **S 强**   | `encoding.ts:20-42` BOM+严格 UTF-8+gb18030 零依赖 vs T 依赖 chardet                                            |
| 任务栏嵌入         | **S 强**   | Rust `strategy/win10.rs                                                                                        | win11.rs` 分策略 + UIA + 2×RegistryWatcher + TrayWatcher + TaskbarCreated 事件驱动 vs T 的 800ms 轮询+手工重建 |
| 歌词偏移           | **S 强**   | per-track `player.lyricOffsets`（`nowPlaying.ts:78`）跨窗口生效 vs T 全局 ±200ms                               |
| 逐字扫光/双行/翻译 | **S 独有** | T 完全没有                                                                                                     |
| 元数据行剔除       | S 略强     | `lyricStripper.ts:34-42` 支持用户关键词+正则                                                                   |

有意思的是 `TaskBarLyrics/app/parser.py:110-124` 的 `pick_primary` 注释里自己承认是抄 SPlayer 的语义。

### 真正值得补进来的（按优先级）

**① 独立 `.lrc/.txt` 歌词库目录的模糊匹配** — 纯 TS，性价比最高

SPlayer-Next 的 `src/services/localLyricRepo.ts:66-83` **只收 `.ttml`**，`:213` 是精确标题查表无模糊，sidecar 只认同目录。这是真空洞。而 T 的 `local.py:159-204` 有完整方案：文件名归一化（`:27-33`，去括号段、只留 `\w`+汉字）→ `SequenceMatcher` 加权打分阈值 0.62 → 再读文件头 120 行 `[ti:]/[ar:]` 打分阈值 1.2（`:67-105`）。

**与退役 TTML 正好互补**：你退役 TTML 后，`localLyricRepo` 会因为只认 `.ttml` 而变成空壳。这一项把它改成吃 `.lrc/.txt`，等于**用你的本地歌词库补回一部分逐字损失**（虽然 LRC 是行级）。这两件事应该合并成一批做。

S 已有 `normalize()` 与 `readFileAutoEncoding` 可直接复用。

**② LRCLIB 作为最后兜底源** — 纯逻辑

T 的 `lrclib.py:66-119` 是无鉴权单 GET + 取 `syncedLyrics`。S 全仓 0 引用 LRCLIB（现有来源是平台 API + AMLL TTML DB + 插件）。

接入要求：**时长校验换成 S 现有的 `durationClose/durationFar` 打分**，缓存落 `lyricCache.ts`，**不要新建平行链路**。注意它给的是行级时间戳，补不了逐字。

**③ Win11 原生 Acrylic 背景 + 强度** — 需跨语言，约 40 行 Rust

T 的 `acrylic.py:88-119` 用 `SetWindowCompositionAttribute`（未公开 API）。S 的任务栏歌词只有 hover 半透明 rgba（`App.vue:334`），全仓无 acrylic/mica/backdrop-filter。语义可 1:1 搬进 `native/taskbar-lyric` 加 `setAcrylic(hwnd, radius, tint)`。

不建议用 CSS `backdrop-filter` 替代——AGENTS.md 明确要求新增 blur 层需论证，且嵌入透明窗效果不等价。

**次优先**：全屏遮挡自动隐藏+降频（T `wintaskbar.py:321-342`，S 无；须配合"隐藏即静默"门控 position 推送）、暂停/离开延时自动隐藏、跑马灯 bounce/恒速/悬停暂停（T `config.py:74-75`，S 只有按进度单向滚动）。

8. **B 站 Referer 的实现约束（推翻本文早期的 webRequest 方案）**：本应用的音频由 Rust `audio-engine`（FFmpeg + reqwest）直接拉流，**不经过 Chromium 网络栈**，所以 `session.webRequest.onBeforeSendHeaders` 注入 `Referer/Origin/UA` 对播放无效。可行路只有两条：给 `audio-engine` 的加载路径传 FFmpeg 的 `http_headers` 输入选项（首选，改动在 Rust 侧），或在主进程起一个与 Otter `BilibiliProxyServer` 等价的本地 HTTP 代理（兜底，多一个端口）。Cookie 本身不受影响——接口请求全在 Node 侧拼 `Cookie:` 头，与 Otter 的现状一致。

**上文的"首选"已被证伪，定死走本地代理**：查证 `~/.cargo/registry/.../ffmpeg_audio-0.3.1/src/http.rs`，`HttpAudioSource` 是 **reqwest 实现**，请求头里只硬编码了 `USER_AGENT = "Lavf/62.12.101"` 与 `Range`，既没有 AVOption 入口也没有自定义头入口，`http_headers` 那套 FFmpeg 协议选项根本不经过这里。除非 fork 该 crate，否则无法给播放流加 Referer。所以：

- 播放流走主进程本地 HTTP 代理（Node `http`，只监听 `127.0.0.1`，端口运行时分配），转发时注入 `Referer/Origin/User-Agent`，透传 `Range` 并回传 `Content-Range/Accept-Ranges/Content-Length/ETag`，`audio-engine` 只需拿到 `http://127.0.0.1:<port>/...`。
- 代理必须做**目标域名白名单**（仅 B 站 CDN 主机），禁止把任意 URL 作为参数转发，否则等于在本机开一个开放代理（SSRF）。
- 封面等由渲染进程发起的图片请求不受此限制影响，那部分可以走 `session.webRequest` 注入头。
